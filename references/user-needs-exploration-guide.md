# 用户需求发散指南(user-needs-exploration-guide)
## 基础指南
本指南列出的发散点是内部检查表，不是给用户的提问清单，发散的目的是在扩大产品需求、找到有价值的产品需求分支的同时，尽可能减小用户负担，仅做定向用户追问，而不是做问卷调查。

发散可以按下述流程进行：

1. **先自答,再发问**  
每个发散点,先尝试基于对话上下文和先验知识自己回答。  
能回答的,作为"假设"输出给用户,让用户判断是否修正。  
不能回答的,才进入下一步。
2. **不能回答的,先评估"必须性"**  
不是所有不能回答的都要问。判断标准:
    - 这个问题的答案是否影响产品方向?(影响小,先用默认值)
    - 不同答案是否导致显著不同的设计?(差异小,先选常见的)
    - 现在不问,后续是否还有机会问?(后续能问,延后)  
只有"影响大、差异大、后续没机会"的才必须问。
3. **必须问的,一次最多 3 个**  
单次对话不超过 3 个追问,超过的拆到下一轮。
4. **每个问题必须带"为什么问"**  
告诉用户这个问题的答案会影响产品的什么决策。  
不带原因的问题,用户答得敷衍,等于没问。
5. **优先用"假设确认"代替"开放追问"**  
"你的产品是 B 端还是 C 端?" → 开放追问,用户要思考  
"我假设这是 B 端协作产品,因为你提到了'部门'和'审批'。  
如果不对告诉我。" → 假设确认,用户只需判断对错

## 发散概览
| 发散点 | 核心问题 | 可能产出的产品需求 |
| --- | --- | --- |
| 用户角色 | 谁用、谁看、谁负责 | 角色权限、管理视图、操作记录 |
| 使用场景 | 什么时候、在哪里用 | 移动端、快捷入口、通知 |
| 任务目标 | 用户真正要完成什么 | 报告、导出、分享、审批 |
| 流程前后 | 前一步和后一步是什么 | 预填、草稿、结果页、下一步操作 |
| 痛点强度 | 高频还是高损失 | 优化交互、风控、核心能力 |
| 替代方案 | 现在怎么绕过去 | 导入导出、截图、同步、人工审核 |
| 信息输入 | 用户需要提供什么 | 默认值、校验、模板 |
| 结果输出 | 结果给谁、怎么用 | 文件、链接、版本、通知 |
| 协作关系 | 是否多人参与 | 分配、评论、审批、状态 |
| 权限责任 | 谁能做、谁负责 | 权限、日志、撤销 |
| 异常状态 | 失败和边界怎么处理 | 重试、空状态、冲突提示 |
| 频率批量 | 单次还是重复处理 | 批量操作、常用模板 |
| 配置差异 | 不同团队是否不同 | 字段配置、规则配置 |
| 数据连接 | 数据从哪来、到哪去 | 导入、同步、接口 |
| 触发机制 | 用户何时知道要处理 | 提醒、待办、订阅 |
| 成功标准 | 怎么判断有效 | 指标统计、效果评估 |
| 业务边界 | 该不该产品化 | 产品化、人工、运营、暂缓 |


## 发散点详情
### 用户角色发散
同一个需求，可能来自不同角色。

很多产品需求错位，是因为只听了提出需求的人，没找到真正使用和承担后果的人。

设问：

+ 谁提出这个需求？
+ 谁实际使用？
+ 谁被结果影响？
+ 谁审批？
+ 谁维护？
+ 谁为错误承担责任？

可能衍生出的产品需求：

+ 普通用户需要快速操作。
+ 管理者需要查看进度和结果。
+ 审核者需要权限和记录。
+ 运营人员需要配置入口。
+ 技术人员需要接口或数据同步能力。

### 使用场景发散
用户在不同环境下做同一件事，产品需求会变。

“用户要一个功能”不够，必须知道他在什么情况下用这个功能。

设问：

+ 用户在什么时候用？
+ 是在办公室、路上、会议中，还是客户现场？
+ 是主动打开产品，还是被通知触发？
+ 是高压场景，还是日常处理？
+ 是单次任务，还是连续任务？

可能衍生出的产品需求：

+ 移动端适配。
+ 快捷入口。
+ 离线查看。
+ 通知提醒。
+ 批量处理。
+ 低干扰模式。
+ 关键操作二次确认。

### 任务目标发散
用户说的是解决方案，而不是最终目标。

用户说“我要导出”，目标可能是“交差、汇报、对账、留痕、迁移数据”。每个目标对应的产品需求不同。

设问：

+ 最终想完成什么？
+ 完成后要交给谁？
+ 交付物是什么？
+ 怎样算完成？
+ 现在卡在哪一步？
+ 为什么需要这个功能，而不是其他方式？

可能衍生出的产品需求：

+ 导出数据。
+ 生成报告。
+ 分享链接。
+ 自动发送。
+ 保存模板。
+ 支持审批。
+ 支持归档。

### 流程前后发散
不要只看用户提出需求的那个点，要看它前后发生了什么。

很多用户需求不是某个功能缺失，而是前后步骤割裂。

设问：

+ 这个动作之前，用户在做什么？
+ 用户从哪里进入？
+ 需要准备什么信息？
+ 完成后要做什么？
+ 是否还有下一步操作？
+ 失败后怎么处理？

可能衍生出的产品需求：

+ 前置筛选。
+ 默认填充。
+ 草稿保存。
+ 结果预览。
+ 后续推荐操作。
+ 错误恢复。
+ 操作历史。

### 痛点强度发散
不是所有用户痛点都值得做。

避免把“用户抱怨”误判成“产品需求”。

设问：

+ 这个问题多久出现一次？
+ 一次会浪费多少时间？
+ 影响多少人？
+ 有没有造成经济损失？
+ 有没有造成客户投诉？
+ 有没有合规风险？
+ 不解决会怎样？

可能衍生出的产品需求：

+ 高频低成本问题，适合优化交互。
+ 低频高风险问题，适合加提醒、确认、权限、记录。
+ 高频高损失问题，适合做成核心能力。
+ 低频低损失问题，可以不做，或交给人工处理。

### 当前替代方案发散
如果用户现在有替代方案，那替代方案里就有真实需求，因为替代方案是用户已经验证过的真实流程。

设问：

+ 现在是怎么解决的？
+ 用 Excel、微信、邮件、截图，还是人工登记？
+ 谁来补这个流程？
+ 哪里最麻烦？
+ 哪里最容易出错？
+ 为什么现有方式还能继续用？

可能衍生出的产品需求：

+ Excel 导入导出。
+ 消息同步。
+ 批量复制。
+ 截图分享。
+ 人工审核入口。
+ 数据校验。
+ 异常标记。

### 信息输入发散
任何产品流程都需要输入信息。

输入越复杂，用户越容易放弃。很多需求最后不是加功能，而是减少用户输入。

要问：

+ 用户需要填写什么？
+ 哪些信息已经存在系统里？
+ 哪些需要用户手动提供？
+ 哪些可以从历史记录推断？
+ 哪些字段容易填错？
+ 哪些字段用户根本不知道？

可能衍生出的产品需求：

+ 字段自动带出。
+ 历史值复用。
+ 必填项减少。
+ 输入校验。
+ 字段解释。
+ 默认值。
+ 模板。

### 结果输出发散
用户要的不是操作本身，而是操作后的结果。

产品需求要定义输出物，否则功能做完也可能无法满足真实使用。

设问：

+ 用户希望看到什么结果？
+ 结果以什么形式出现？
+ 谁会看这个结果？
+ 需要下载、分享、打印、同步，还是存档？
+ 结果是否需要被再次编辑？
+ 是否需要保留版本？

可能衍生出的产品需求：

+ 结果页。
+ 下载文件。
+ 分享链接。
+ 报告模板。
+ 版本记录。
+ 导出权限。
+ 结果通知。

### 协作关系发散
很多需求不是单人完成的。

拆清协作关系，产品容易只做出“个人工具”，但用户需要的是“多人配合完成一件事”。

设问：

+ 这个任务是否涉及多人？
+ 谁发起？
+ 谁处理？
+ 谁确认？
+ 谁被通知？
+ 是否需要评论？
+ 是否需要移交？
+ 是否需要审批？

可能衍生出的产品需求：

+ 任务分配。
+ 评论区。
+ 状态流转。
+ 审批。
+ 通知。
+ 负责人变更。
+ 操作记录。

### 权限与责任发散
用户能不能做，比用户想不想做更重要。

权限不是后补项。很多 B 端产品需求，权限一变，功能结构就会变。

设问：

+ 谁可以看？
+ 谁可以改？
+ 谁可以删除？
+ 谁可以导出？
+ 谁可以审批？
+ 误操作后谁负责？
+ 是否需要追溯？

可能衍生出的产品需求：

+ 角色权限。
+ 字段权限。
+ 操作权限。
+ 审批权限。
+ 日志记录。
+ 撤销。
+ 敏感操作确认。

### 状态与异常发散
产品不能只设计成功路径。

异常状态能暴露真实使用边界。只讨论理想流程，产品需求会很脆弱。

设问：

+ 如果数据为空怎么办？
+ 如果提交失败怎么办？
+ 如果权限不足怎么办？
+ 如果网络中断怎么办？
+ 如果多人同时编辑怎么办？
+ 如果用户填错了怎么办？
+ 如果任务超时怎么办？

可能衍生出的产品需求：

+ 空状态提示。
+ 失败重试。
+ 权限申请。
+ 草稿保存。
+ 冲突提示。
+ 校验规则。
+ 超时提醒。

### 频率与批量发散
同一个动作，单次和批量是两种产品需求。

高频需求要减少步骤。批量需求要减少重复劳动。

设问：

+ 用户一天做几次？
+ 一次处理一个对象，还是多个对象？
+ 是否需要批量选择？
+ 是否需要批量导入？
+ 是否需要批量修改？
+ 是否需要保存常用操作？

可能衍生出的产品需求：

+ 批量操作。
+ 快捷操作。
+ 默认筛选。
+ 常用模板。
+ 最近使用。
+ 自动保存。

### 个性化配置发散
不要一上来就做复杂配置，配置不是越多越好。判断是否存在差异。只有当差异稳定存在，才值得做配置。

设问：

+ 不同用户的规则是否一致？
+ 不同团队是否有不同流程？
+ 字段是否固定？
+ 提醒时间是否固定？
+ 审批人是否固定？
+ 输出格式是否固定？

可能衍生出的产品需求：

+ 可配置字段。
+ 可配置提醒时间。
+ 可配置模板。
+ 可配置审批规则。
+ 默认配置。
+ 管理员设置入口。

### 数据与系统连接发散
用户需求经常依赖外部系统或已有数据。

如果数据来源没弄清楚，功能界面设计得再完整也无法落地。

设问：

+ 数据从哪里来？
+ 是否需要同步其他系统？
+ 是否需要导入历史数据？
+ 是否需要向外部系统推送？
+ 是否需要接口？
+ 数据更新频率是多少？
+ 数据不一致时以谁为准？

可能衍生出的产品需求：

+ 数据导入。
+ 数据同步。
+ 接口开放。
+ 字段映射。
+ 冲突处理。
+ 同步日志。
+ 手动刷新。

### 触发机制发散
用户不一定会主动进入页面操作。

提醒类需求不能只问“要不要提醒”，要问“什么事件发生时，提醒谁，提醒什么，提醒后能做什么”。

设问：

+ 用户什么时候意识到要处理？
+ 是自己发现，还是系统提醒？
+ 是时间触发，状态触发，还是别人操作触发？
+ 是否需要提前提醒？
+ 是否需要重复提醒？
+ 提醒给谁？

可能衍生出的产品需求：

+ 定时提醒。
+ 状态变化提醒。
+ 异常提醒。
+ 待办。
+ 消息订阅。
+ 通知聚合。
+ 通知免打扰。

### 成功标准发散
没有成功标准，产品需求无法判断是否有效。

成功标准不是汇报用的装饰，应该反过来决定需求要做到什么程度。

设问：

+ 上线后你怎么判断它有用？
+ 节省了多少时间？
+ 错误减少多少？
+ 完成率提高多少？
+ 投诉减少多少？
+ 是否减少人工介入？
+ 是否提升转化或留存？

可能衍生出的产品需求：

+ 统计埋点。
+ 完成率看板。
+ 操作耗时统计。
+ 错误率统计。
+ 提醒触达率。
+ 任务处理率。

### 业务边界发散
要判断这个需求该不该由产品解决。

发散不是为了把需求越扩越大，而是为了看清哪些需求不该做。

设问：

+ 这是个普遍问题，还是某个客户的特殊要求？
+ 是产品问题，还是培训问题？
+ 是流程问题，还是系统能力缺失？
+ 是短期需求，还是长期需求？
+ 做了会不会影响其他用户？
+ 有没有更便宜的解决方式？

可能衍生出的处理方式：

+ 进入产品需求池。
+ 先做运营方案。
+ 先做配置方案。
+ 只支持重点客户。
+ 暂不处理。
+ 用人工服务解决。
